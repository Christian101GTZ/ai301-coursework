## Who I am in threads

I'm Christian, and I previously contributed to PathReview during
CodePath's AI 201 course. I have some experience with open source, but
I'm still learning.

My goal in this repository is to report bugs, work on issues, and
improve my skills. Maintainers can expect simple and clear
communication from me about what I've tried, what I've found, and
anything I'm unsure about.

## Rules I write by

### Rule: Keep my communication simple and clear

I want my comments to be easy to understand. I should explain what I'm
trying to say without adding unnecessary details or making things more
complicated.

- Wrong: "The implementation seems to have some unexpected behavior
  that might be related to several different parts of the code."
- Right: "I noticed that this part of the code isn't working as
  expected. I'm still trying to understand what is causing it."

### Rule: Explain what I actually tried

When reporting a bug or working on an issue, I should explain what I
did and what happened. I shouldn't assume that maintainers already know
what I'm talking about.

- Wrong: "The code doesn't work. I think there's a bug."
- Right: "I ran the code and got an error. Here are the steps I
  followed and the error I received."

### Rule: Be honest about what I know

I'm still learning, so I shouldn't pretend to understand something when
I don't. I should separate what I've confirmed from what I think might
be causing the problem.

- Wrong: "The problem is definitely caused by this function."
- Right: "I think this function might be causing the problem, but I
  haven't confirmed it yet."

### Rule: Be open to feedback

I want to improve as a contributor, so I should be willing to listen to
suggestions and ask questions when something isn't clear. I don't need
to agree with everything, but I should explain my reasoning
respectfully.

- Wrong: "I don't think your suggestion will work."
- Right: "I see what you're suggesting. Could you explain how this
  would work? I want to make sure I understand it before making
  changes."

### Rule: Don't promise more than I can do

I should be realistic about my experience and availability. If I'm
interested in working on an issue, I can say so without promising that
I'll finish it by a certain time.

- Wrong: "I'll have this issue fixed by tomorrow."
- Right: "I'd like to work on this issue. I'll take a look at the code
  and share what I find."

## Things I never post

- I don't claim that I fixed or tested something unless I've actually
  done it.
- I don't promise to finish an issue by a certain date if I'm not sure
  I can.
- I don't pretend to understand something just to sound more
  experienced.
- I don't post comments that are unnecessarily complicated or difficult
  to understand.
- I don't blame maintainers or other contributors when something goes
  wrong.
- I don't post guesses as facts. If I'm unsure about something, I say
  so.

The main idea behind my voice guide is that I want to communicate
clearly, be honest about my experience, and make it easier for
maintainers to understand what I'm doing. I don't need to sound like an
experienced developer to make a useful contribution.
